### 目标

让 budingx 的 TUI 在**结构层**（四区骨架、键位系统、渲染管线、状态栏）与**能力层**（项目指令、技能/MCP、受控 hooks、联网来源、无头协议、制品安装）同时达到下一轮可验收基线：

1. **结构可判定**：参考仓的用户可见表面清单中属 P0 的五项逐项有 PASS/PARTIAL/MISS 判定与行为用例。
2. **能力可日常使用**：项目指令、技能、MCP、hooks、网页抓取、无头 CLI 六类能力在真实进程下可用且不破坏既有回合契约。
3. **协议可复用**：命令注册表三型、上下文键位系统、MCP JSON-RPC、hooks 输出契约、无头 stream-json 均为**显式契约**，可供后续轮次复用。
4. **制品可交付**：实际 tarball 在仓库外隔离安装并完成一次核心任务，npm dry-run 骨架就绪而不上传。

### 边界规则（不可突破）

- **用户数据根唯一**：`~/.budingx`（`os.homedir()` 解析）。不读写 `~/.claude`，不硬编码用户名、盘符或 cwd。
- **参考仓只读**：只读理解行为事实与公开协议，不复制源码、提示词、内部类型；实现独立编写。
- **独立来源可判定**：SP006 改动的每个源码文件都要在 AST 复核映射表中有对照项或「无对应参考模块」说明；命中项必须有处置结论。
- **协议先行**：命令三型、键位上下文、MCP JSON-RPC、hooks 输出、无头事件均为显式类型契约，测试以契约 fixture 锁定。
- **失败不扩散**：MCP/hooks/联网来源任一失败都不得中断会话或丢失已产生的回合结果。
- **审批不可绕过**：MCP 工具、网页抓取、hooks 触发的写操作都走既有权限审批；不得新增免审通道。
- **零测试不算通过**：每条 AC 至少各有一例单元与一例功能/真实进程用例；未执行项标 UNVERIFIED 并写恢复条件。

## 不变与风险

| 项 | 说明 |
| --- | --- |
| 不变 1 | 权限仍为三档；本轮任何新工具都不得绕过审批 |
| 不变 2 | `core` 保持零 IO；新增能力按 `core`（契约）/ `storage`（持久化）/ `tui`（宿主）分层 |
| 不变 3 | 既有测试全绿是硬门槛；新增能力不得降低既有断言强度 |
| 风险 R-S1 | MCP 协议面大，易越界；本轮限定 stdio + tools 能力子集，其余显式记 NOT_IMPLEMENTED |
| 风险 R-S2 | 帧缓冲差分与 Ink 的重绘模型可能冲突；先做可断言的差分单元，再接渲染层，不做全屏重写 |
| 风险 R-S3 | hooks 可执行任意命令，属安全面；默认只读用户配置、命令超时可控、失败降级 |
| 风险 R-S4 | 本轮范围大；实现按「P0 骨架 → 命令注册表 → 能力目录 → 制品」四波推进，每波结束跑既有回归 |
| 风险 R-S5 | 合入 master 与发布不在本轮授权内，交付物停在功能分支 |
