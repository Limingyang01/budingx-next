# 权限模式与审批控制 · permission-controls

状态：DRAFT｜版本：v0.2（2026-11-17 T18 能力对齐修订）｜迭代：SP003｜来源身份：USER_CONFIRMED（2026-11-17 r6 三模式固定决定 + 路线图功能名与出口门槛）+ MODEL_PROPOSED（规则语法与审批交互细节）

## 来源与目标

- USER_CONFIRMED（2026-11-17 r6）：「TUI 权限模式固定为三种——**仅可查看**（只读文件与分析，不修改代码）、**工作区内修改**（允许编辑工作区文件）、**完全权限**（自动执行，无需反复确认）；替代参考仓 7 模式与早前「四类语义」提议，由 SP003/SP004 交付……模式切换交互、命令执行边界与安全底线在 SP003 开轮细化，**不得借「完全权限」绕过 deny 规则与凭据保护**。」
- 路线图 SP003（USER_CONFIRMED）：功能目录 permission-controls；出口含「三权限模式切换与边界有回归」。
- 能力矩阵（USER_CONFIRMED 范围）：CAP-L3-06 权限模式集合（用户固定三模式）、CAP-L3-07 权限规则匹配与规则管理、CAP-L3-08 被遮蔽规则检测与拒绝追踪（建议项）、CAP-L3-10 分类器自动审批（可选，不作为默认路径）。
- 排查文档 SP003 条目（参考事实，仅行为对照）：权限弹窗三档 + 会话记忆按目录限定 + bash 可编辑前缀规则 + Yes/No 反馈输入态；规则语法 `Tool(content)` / bash 前缀 / 路径 gitignore 语义 + 别名归一 + 注入防护；参考仓 7 模式仅作基线事实。
- 当前仓库事实（2026-11-17，`master` = `b0ffc9e`）：SP002 已实现最小审批闭环——`ApprovalGateway` 端口、`requiresApproval` 钩子、`approval_requested`/`approval_resolved` 事件、Ink 侧 `InkApprovalGateway`（仅 allow/deny 两种结局），**没有任何权限模式概念**。
- 本轮目标：把「谁能做什么」变成一层可判定、可解释、可回归的策略：模式决定默认放行/默认审批，规则决定例外，审批提供人工兜底，底线规则不可绕过。

## 范围与非目标

**范围**：三权限模式的定义、默认模式、切换方式（交互 + 命令）与显示；模式 × 工具能力的判定矩阵；写操作的审批三档（允许一次 / 本会话内对该目标记住 / 拒绝）；规则（按工具、按路径、按内容前缀）的增删改查与匹配；规则被更高优先级规则遮蔽时的检测与可见提示；拒绝记录与「拒绝后仍能继续工作」；底线规则（凭据与密钥文件路径、越界路径、`~/.budingx` 用户数据）在所有模式下均拒绝；模式与规则的持久化边界。
**非目标**：命令执行与 shell 审批的完整形态（SP004，本轮只提供可复用判定接口与模式语义）；按目录/按会话的自动记忆细化（只做最小可用形态）；风险评分与分类器自动审批（CAP-L3-10 可选，不作为默认路径）；MCP 工具信任、项目级配置继承（SP006）；团队权限传播（SP011）。

## 依赖、风险与开放问题

- 依赖：SP002 的 `ApprovalGateway`/`ApprovalDecision` 端口与审批事件（需扩展为三档结局，属本轮契约变更，须在设计中登记版本）；workspace-tools 的能力分类（读类/写类）与路径解析；storage 的用户数据根规则（`~/.budingx`）用于底线判定。
- 许可与来源：规则语法按行为事实**自写解析器**，不搬参考仓实现；不引入第三方规则引擎。
- 风险：模式语义含糊导致用户误判 → 模式名、判定矩阵与当前模式在 UI 可见；「完全权限」被当作万能钥匙 → 底线规则独立于模式判定，且有负向回归；规则语法过强带来注入风险 → 规则内容只作为数据解析，不拼接执行；持久化规则含路径信息 → 规则文件按用户数据根存放，不含凭据。
- OPEN：审批三档的默认档位与「记住」的粒度（按工具+路径）由设计定稿；规则文件的具体 schema 与迁移规则（首版无历史 schema，写入版本号）。
