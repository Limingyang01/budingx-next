# 核心边界与架构不变量 · core-boundaries

状态：APPROVED（规格已验收，2026-11-16；实现未批准）｜版本：v1｜迭代：SP001｜来源身份：MODEL_PROPOSED + USER_CONFIRMED（Core 零框架、Node-only）

## 来源与目标

### 用户材料（USER_CONFIRMED）

- 2026-11-16：「不能直接使用 `D:\extra_project\buding-worker-space` 里的代码……你可以参考它的核心实现，再复刻出来」——即：需要自有实现，且需要划清哪些是「核心」必须自有。
- 2026-11-16 决定：**Core 零框架，TUI 层允许 MIT 终端框架**。
- 2026-11-16 追加：「基于 node，不要依赖于 bun」。
- `AGENTS.md`（USER_CONFIRMED）：统一主分支 master；Node + TypeScript；产品数据统一 `~/.budingx`；禁止读取/回退 `~/.claude`；各模块独立构建/打包，共享契约与 Core 不按端复制；不预先引入通用插件框架或全套微服务。

### 目标

定义新仓的**责任边界与不变量**，使 21 轮路线图里的 TUI / Desktop / VS Code 三端能共享一套 Core 而不互相绑架，并让「达到原 Agent 水平」这条路线在架构上可落地。

本轮只定**边界、不变量与目录蓝图**，不定 API 字段、不定框架版本、不定数据库 schema（那些属于 SP002–SP005 的设计）。

### 现状（MODEL_PROPOSED）

- 既有 `docs/architecture.md` 已给出稳定的逻辑边界（TUI/Desktop/VS Code → 自有应用用例 → 自有 Agent Core → 模型适配器 / 工具执行与审批 / 会话与配置仓库），但明确标注为 DRAFT，且没有落到具体目录、不变量与可检查的约束。
- 新仓目前只有 `src/tui` 一个模块，尚无 Core、Provider、Tools、Storage 目录，也没有跨端契约。

## 范围与非目标

### 范围

- 四层责任（交互 / 工具 / Agent / 平台）到新仓目录的映射。
- Core 层不可违反的不变量清单（可被检查的形式）。
- 四个方向性契约的**责任边界**（谁定义、谁消费、失败时谁负责），不定义字段。
- 共享状态与所有权规则：会话归属、数据根、凭据作用域。
- 端无关与可取消性的最低要求（因为 SP002–SP007 必须保持宿主无关）。

### 非目标

- 不定义任何具体 API 字段、事件 schema、JSON 格式（留给 SP002）。
- 不选择终端 UI 框架的具体包与版本（留给 SP002，需按本轮验收方式证明能力等价）。
- 不设计权限规则语法、压缩算法、存储 schema（SP003/SP005）。
- 不引入插件框架、微服务、常驻网关进程（路线图明确不预先引入）。
- 不实现 Core 代码（本轮只交规格）。

| AC-04 | 边界设计存在 | 检查工具层是否被约束为必须经审批/权限接口、且有输入校验与输出上限 | 明文不变量 | 人工核对设计 |

| AC-06 | 边界设计存在 | 检查会话所有权规则 | 单写者规则明确；并发写者拒绝而非互相覆盖 | 人工核对设计 |
| AC-07 | 边界设计存在 | 检查取消传播规则 | 从 UI 到 provider / 工具 / 子进程 / 子代理全链路写明 | 人工核对设计 |
| AC-08 | 边界设计存在 | 检查不可信内容处理规则 | 文件、网页、工具输出、skill、仓库指令均视为不可信输入，不提升权限 | 人工核对设计 |
| AC-09 | 边界设计存在 | 检查凭据边界 | 凭据不写普通共享 JSON、不进日志、按作用域隔离 | 人工核对设计 |

| AC-11 | 边界设计存在 | 检查三端共享 Core 的方式是否避免「TUI 成为其他端后端前置」 | 明文禁止；各端独立运行 | 人工核对设计 |

| AC-13 | 边界设计存在 | 检查是否把旧仓内部类型/提示词/全局状态列为复用对象 | 明确列为禁止迁入 | 人工核对设计 |

失败/边界场景覆盖：AC-03（厂商类型泄漏）、AC-06（并发写者）、AC-08（提示注入提权）、AC-11（TUI 变成单点后端）。

不适用说明：本轮不涉及真实跨进程/UI/live 验证，均为设计层人工核对；运行期证据由 SP002 起补。

## 依赖、风险与开放问题

- 依赖：`docs/architecture.md`（逻辑边界草案）、`AGENTS.md`（数据根与 Git 约定）、[能力清单](../capability-baseline/capability-manifest.md) 的分层。
- 来源与许可：Core 全部自研；不复用旧仓的 Agent 循环、提示词、SDK 类型、全局状态（`AGENTS.md` 与 [独立实现边界](../../../docs/independent-development.md) 已明文禁止）。终端 UI 框架为 MIT 第三方组件，只允许出现在 TUI 渲染层。
- 风险：
  - 「Core 零框架」若不配可执行检查，会在数轮后被打破。SP001 已要求把依赖白名单写成可执行检查项，交由 SP002 建。
  - 边界划得过细会产生大量接口层。本轮按「四层 + 四个契约方向」保持最小，其余细节下沉到各轮设计。
  - 本仓 `src/tui` 现有代码把 provider 调用直接写在 CLI 里；SP002 拆分时需要一次明确的迁移，属于 SP002 范围而非本轮。
- 开放问题：
  - OPEN-01：Core 是否需要独立的 npm 包（供 Desktop/VS Code 复用）还是同仓目录。默认：同仓 `src/core` 目录 + 独立构建产出，留待 SP002 确认。
  - OPEN-02：跨端共享存储的并发模型（单写者 vs 租约）。默认：会话级单写者 + 其他端只读观察，SP008 再定落地。
  - OPEN-03：终端 UI 框架候选与其 MIT 许可确认。默认：SP002 选型并登记 `THIRD-PARTY-NOTICES.md`。
