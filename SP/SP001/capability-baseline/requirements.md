# 能力盘点与基线 · capability-baseline

状态：APPROVED（规格已验收，2026-11-16；实现未批准）｜版本：v1｜迭代：SP001｜来源身份：MODEL_PROPOSED + USER_CONFIRMED（目标与取证决定）

## 来源与目标

### 用户材料（USER_CONFIRMED）

- 2026-11-16，原话要点：「使用 sdd 开发流程，按照目前设计的 SP001 的迭代功能生成设计文档，实现要求达到 `D:\extra_project\buding-worker-space` 里的 tui 水平，但是不能直接使用 `D:\extra_project\buding-worker-space` 里的代码，因为这是没有开源的，你可以参考它的核心实现，再复刻出来。」
- 2026-11-16 决定：本轮**只交规格，不写产品代码**。
- 2026-11-16 决定：对照基线**静态盘点 + 旧仓自证行为**，不运行旧 Agent、不读取旧仓凭据。
- 2026-11-16 决定：旧仓可**读机制、不抄代码**；所有实现独立编写。
- 2026-11-16 决定：**Core 零框架，TUI 层允许 MIT 终端框架**。
- 2026-11-16 追加：「基于 node，不要依赖于 bun」。与 `AGENTS.md` 既有约定一致（禁止 Bun，Node >= 22.18）。

### 目标

把「达到原 Agent 的 TUI 水平」固定成一张可验收的能力清单，作为 SP002–SP016 每一轮的输入与每一轮出口的对照依据。

### 现状（MODEL_PROPOSED，基于本轮只读盘点）

- 对照基线：`buding-worker-space` 中 `budingx` 0.5.0（私有、未开源）。`src/` 共 2,360 个 TS/TSX 文件 / 602,826 行；其中 TUI 可交互层（components + ink + screens + hooks + commands + keybindings + vim）约 871 文件 / 16.6 万行；工具层 58 个工具目录 / 227 文件 / 54,630 行；92 个命令目录 + 20 个散文件命令；28 个 hook 事件；7 种权限模式；11 项数据迁移；无头输出支持 text / json / stream-json。
- 对照基线的终端渲染不是直接用上游渲染库，而是自研了渲染引擎（reconciler、布局、ANSI 解析、终端事件层，约 2.0 万行）。
- 新仓现状：`src/tui` 共 4 个源文件 / 329 行（`cli.ts` 152、`provider.ts` 121、`config.ts` 56），行式 readline 输入，6 个斜杠命令，仅文本 SSE 输出，会话只在内存，无工具、无文件访问、无持久化、无权限模型、无无头结构化输出。
- 差距量级：距基线的 L1 交互层约差 16 万行量级，L2/L3/L4 尚未起步。**目前与基线一致的只有 Node 版本约束与「不读 `~/.claude`、用户数据根为 `~/.budingx`」两条约定。**

### 目标水平如何定义（MODEL_PROPOSED）

按能力依赖自下而上分四层：L1 交互 / L2 工具 / L3 Agent / L4 平台。每一项能力给稳定 CAP ID，落在 [能力清单](capability-manifest.md)。

## 范围与非目标

### 范围

- 产出 [能力清单](capability-manifest.md) v1：分层能力项、基线证据、目标状态、归属迭代、验收方式、必需性。
- 固定清单的编号与变更规则、覆盖度计算口径。
- 登记来源台账与许可处理决定。

### 非目标

- 不运行原 Agent，不采集其成功率、耗时或成本。**本轮不存在原产品效果基线。**
- 不实现任何产品代码，不改 `src/tui` 运行时行为。
- 不复制旧仓源码、提示词、内部类型、bundle、配置或历史记录。
- 不逐文件改写旧仓代码冒充独立实现。
- 不在 SP001 决定终端 UI 框架的具体选型（留给 SP002，按本清单的验收方式执行）。

## 验收条件

| AC ID | 前置条件 / 输入 | 操作 | 可观察结果 | 验证方式 |
| --- | --- | --- | --- | --- |
| AC-01 | 原 Agent 处于只读可访问状态 | 按目录结构、公开描述与规模统计做只读盘点 | 产出分层能力事实与规模数字，不含源码、提示词、密钥、聊天历史 | 人工核对 + 源台账登记 |
| AC-02 | 能力清单 v1 存在 | 逐行检查每项是否有基线证据、目标状态、归属 SP、验收方式、必需性 | 无空列、无占位符；ID 唯一且不重复 | 人工核对清单 |
| AC-03 | 能力清单存在 | 计算必交项总数与覆盖度分母 | 分母固定为必交项数；建议/可选不计入分母 | 人工核对 + 清单统计节 |
| AC-04 | 能力清单存在 | 检查每个 CAP ID 是否唯一、是否复用已废弃语义 | ID 唯一；废弃项保留并标 DEPRECATED | 人工核对清单 |
| AC-05 | 旧仓存在同名能力 | 检查清单中旧仓特有能力（语音输入、插件体系、Notebook 编辑、PR 集成等） | 未被悄悄丢弃；明确标 `范围外` 或 `可选` 并写理由 | 人工核对清单 |
| AC-06 | 用户已确认「五类高级能力为必交」 | 检查团队/浏览器/Computer Use/远程/IM/定时在清单中的必需性 | 全部为 `必交` 且有归属 SP | 人工核对清单 |
| AC-07 | 清单存在 | 检查每项的验收方式是否与 [技术栈与验证路由](../../../skills/buding-sdd/references/technology-map.md) 的证据分类一致 | 每项标注了证据层；未把 fixture 当 live | 人工核对清单 |
| AC-08 | 清单存在 | 检查是否用命令数量/文件行数当达标口径 | 覆盖度只按必交项 PASS 计；数量类指标仅作背景事实 | 人工核对清单 + 摘要 |
| AC-09 | 旧仓不可读或不可访问时 | 重跑本需求 | 清单标注「基线证据缺失」项，不臆造 | 人工核对（恢复条件见下） |
| AC-10 | 本仓存在 | 检查清单是否声明与现有 `src/tui` 的差距，不把现状说成基线 | 差距事实与当前一致项均写明 | 人工核对需求正文 |

必须补充的失败/边界场景（已覆盖）：AC-09 处理基线不可访问；AC-02/AC-04 处理清单自身的完整性失败；AC-03/AC-08 处理「用数量充数」的伪达标。

不适用说明：AC-01 的「运行旧 Agent 取效果基线」不适用，因用户本轮明确选择静态盘点。

## 依赖、风险与开放问题

- 依赖：只读访问 `D:\extra_project\buding-worker-space`（已具备）；`docs/agent-capability-matrix.md` 与 `docs/iteration-plan.md` 的既有能力条目。
- 来源与许可：旧仓私有未开源，仅作行为与结构参考，处理决定见清单末节与 [独立实现边界](../../../docs/independent-development.md)。本仓 `src/tui` 为自有 MIT。
- 风险：
  - 静态盘点只能给出「有没有」，给不出「好不好用」。因此覆盖度只用于追踪交付进度，**不能作为「达到原 Agent 水平」的结论**。
  - 清单粒度过粗会漏能力，过细会变成实现清单而失去验收价值。本轮按「用户可见能力」粒度切分，工具族与命令族按族聚合。
  - 旧仓的 fork 渲染器是其「水平」的一部分，但其复现成本极高；目标状态允许换实现（用上游 MIT 框架），但必须由 SP002 证明等价能力不缺失。
- 开放问题：
  - OPEN-01：能力清单的 `建议`/`可选` 项是否在后续轮次被用户升格为 `必交`。默认不升格，升格需用户确认。
  - OPEN-02：原产品的效果基线何时采集 —— **已决（用户 2026-11-16，全局 O5=B）**：不授权采集；效果对比永久采用「自有能力测量 + 能力清单覆盖度」口径，原产品效果维度永久 UNVERIFIED 且不再寻求恢复。
  - OPEN-03：是否把「原 Agent 的具体版本号与 commit」写入清单作为可追溯锚点。本轮记录 `budingx` 0.5.0 与本地路径，具体 commit 未采集（未授权读取旧仓 Git 历史）。
