## 来源与目标

- **USER_CONFIRMED**（2026-11-24 用户指令「/buding-sdd 开始SP010，先不要直接开发」）：启动 SP010，先完成文档。路线图 SP010 行的范围含「修复影响高级能力接入的 Core 缺陷，交接稳定基线」。
- **USER_CONFIRMED**（路线图 SP011–SP014 行与[能力矩阵](../../../docs/agent-capability-matrix.md)）：团队、浏览器、Computer Use、定时任务是必交能力，由 SP011–SP014 交付；SP010 负责它们**接入前**的 Core 缺陷与基线，不代替它们实现功能。
- **MODEL_PROPOSED**（本文件）：核查口径、缺陷归属规则、必修项清单与交接格式。设计阶段定稿并随设计自审。

### 目标

1. 对 SP011–SP014 各自依赖的 **Core 契约**做一次只读核查，产出可追溯的 PASS/GAP 结论；
2. 修复其中**属于 Core 缺陷**的部分（含评估口径与产品不一致的必修项），按红绿验证推进；
3. 明确**属于新能力**的部分并交回 SP011–SP014，本轮不实现；
4. 把稳定基线、已修缺陷与剩余缺口交接给下一轮。

### 非目标

- 不实现团队消息/租约、浏览器控制、桌面控制、定时器等产品功能。
- 不改三档权限语义（仅可查看 / 工作区内修改 / 完全权限），不引入第四档模式。
- 不改 `~/.budingx` 数据根约定，不读取或迁移真实用户数据，不触碰 `~/.claude`。
- 不为「让高级能力更容易做」而提前重构 Core 架构；只修可被证据证明的缺陷。
- 不做发布、打标签与远端操作。

## 范围

### 1. 接入前置核查（readiness probe）

对四个方向逐项列出 **Core 契约要求 → 当前实现状态（PASS/GAP）→ 证据**，至少覆盖：并发与归属、任务/成员唯一性（租约）、审批在无人值守下的语义、工具输出上限与大附件、事件与转录契约、跨进程与崩溃恢复、取消与预算传播。 每行记录参考行为、启用条件和相对源码位置，再核对本仓契约、证据与差异归属。团队创建、成员消息、团队任务租约、调度启用和调度器租约分别列项。

每个 GAP 必须标注归属之一：

- **缺陷**：当前实现与已声明契约不符或存在不一致 → 本轮修复（AC-CR-02）；
- **新能力**：SP011–SP014 的功能本体 → 交回对应迭代，本轮只记录；
- **测量口径**：属评估器而非产品 → 归 [coding-parity-checkpoint](../coding-parity-checkpoint/requirements.md)（如 D1）。

### 2. 缺陷修复

- **入口**：中期检查暴露、且归因为 Core 的失败（`LOC_ERR` / `MOD_ERR` / `LOOP` / `BUDGET` 中属 Core 者）、readiness 核查中的「缺陷」类 GAP、以及下列必修项。
- **必修项 D1（口径不一致）**：移除固定的 8 轮截断，评估回合上限仅由版本化预算档提供。达到预算终止条件时保留 `BUDGET` 终态，见 [AC-CP-03](../coding-parity-checkpoint/requirements.md#验收条件)。
- **D2（工具结果）**：大文本核对长度、截断标记和原成功状态，真实错误核对原错误码与熔断计数。截图须在消费端可解码；二进制须可完整读取并匹配预期摘要。附件引用须先解析再核验。当前只有文本通道时，将媒体能力缺口交 SP012/SP013。
- **D3（无人值守审批）**：需新审批时检查动作是否执行、当前运行是否在无人输入时结束、调度方能否取得原因并通知。逐段核对权限网关、宿主回执与调度责任，按证据归属缺口。

### 3. 交接

readiness 结论、已修缺陷清单（含红绿证据及最终候选受影响验收项的复跑记录）、未修缺陷与归属、新盲测批次登记，供 SP011–SP014 直接引用。交接时附最终候选身份及制品摘要，并同步迭代汇总、`docs/current-status.md` 与产品说明书。

## 依赖、风险与开放问题

- 依赖：[coding-parity-checkpoint](../coding-parity-checkpoint/requirements.md) 的中期运行结果（失败归因）是缺陷入口的主要来源；SP009 0.9.2 已合入 master；`src/core` 与 `src/host` 的现有测试为回归基线。
- 风险：readiness 核查易滑向「顺手实现」。控制方式是归属三分法与「本轮只修缺陷」的硬边界；发现新能力一律记录并交回。
- 风险：改动 Core 会影响 TUI、无头与 serve 三个入口；每项修复必须跑全量 `npm test` 并核对三个入口的行为未变。
- **OPEN-1**：子代理预算与熔断阈值在「父任务 + 多成员」场景下是否需要分计量，需 SP011 的真实形态确定；本轮只记录，不预设新阈值。
- **OPEN-2（已解决）**：SP009 短路径补丁 `50e558f`／`03ad128` 已合入 master `74c5156` 并推送，本轮基线包含该修复；实施前仍需复核实时 refs。
- **OPEN-3**：本轮不修改 `~/.budingx` schema；若修复需要持久化字段变更，须先在设计中说明迁移与旧 fixture 兼容。
