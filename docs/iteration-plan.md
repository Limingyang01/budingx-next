# budingx-next 迭代路线图

状态：MODEL_PROPOSED / 待审阅。版本：r3；更新：2026-11-16。

用户已授权制定 SP 数量和编号，尚未授权按此计划启动 SDD 或产品开发。当前无产品实现；下文均为计划和建议验收门槛，不是通过记录。后续 Agent 必须先读本文件、[迭代管理](../SP/README.md)、[当前状态](current-status.md)和目标迭代记录，核实最新用户授权。

## 目标与安排依据

USER_CONFIRMED：独立实现自己的 Coding Agent；使用 Node.js + TypeScript、不依赖 Bun；主线 master；TUI、Desktop、VS Code 独立安装和使用，允许共享模型和历史；可接入未来手机端；效果达到原 Agent 的实际工作能力。项目没有需求 ID，按 SP 版本号和具体功能/优化目录组织；需要建设 TUI npm 一键发布能力，未来由 publish 入口直达 npm，当前不执行发布。

配套必读：[能力与验收矩阵](agent-capability-matrix.md)、[高级能力功能拆分与验收](advanced-capabilities-plan.md)、[TUI npm 一键发布方案](npm-release-plan.md)。它们是本路线图的组成部分；功能名称作为索引，不引入需求 ID。

现扩展为 **21 个 SP**。SP001–SP011 保留编码核心、三端、共享和初版交付路线；SP012 改为中期编码效果检查，不再承担完整替代结论。SP013–SP019 分别交付团队、浏览器、Computer Use、远程/H5、四类 IM 和定时任务；SP020 完成全能力跨端集成与升级发布验证，SP021 才作完整替代验收。

USER_CONFIRMED（本轮新增）：Computer Use、多代理团队、远程访问、IM、定时任务正式纳入必交范围，目标完整替代原 Agent。不能在 SP001 将这五类能力重新降为候选；具体技术、交互和验收阈值仍为 MODEL_PROPOSED，尚未启动实施。原有基本编码功能同样是完整替代的必交范围。

后续补充授权：单独实现并验证 MIT 简易聊天 TUI，作为 bootstrap 0.1.0 发布 npm；这不是启动完整 21 轮 SDD。每个完成交付的 SP 更新产品版本，规范见 [版本管理](versioning.md)。用户数据统一由当前用户 home 解析为 `~/.budingx`，禁止硬编码用户名/盘符或使用 `~/.claude`。
这是依赖顺序，不是每轮固定一周的工期承诺。每轮以出口门槛为准；模型访问、评测、平台打包等工作量尚未实测，不给出虚假完成日期。某轮过大可拆分后续编号，已使用编号不改名或回收，更新本表与影响记录。

“原 Agent”暂按用户当前使用的原产品行为理解，具体版本和必需能力在 SP001 固定。只用合法可使用的公开接口和黑盒行为建立对比，不复制旧实现、内部类型、提示词或 bundle。没有可运行的合法基线时，只能报告自有能力测量，不宣称对齐成功。

## 如何证明达到原 Agent 效果

以下为 MODEL_PROPOSED 验收方案，SP001 需与用户固定，后续不能为了通过临时换任务、模型或降低门槛。

> **用户决议（2026-11-16，SP001 O5=B，USER_CONFIRMED）**：不授权采集原产品效果基线。本节中「与原产品对照运行」「可比集完成率相对原产品下降不超过 5 个百分点」及「每题双方各运行」条款**废除**；效果验收永久采用「自有能力测量 + 能力清单覆盖度 + 保护用例全通过 + 用户真实试用」。其余条款（任务快照、盲测、预算、统计纪律、失败归因）继续有效，适用于自有测量。下文保留原文作历史，按本决议执行。

1. 建立至少 30 个版本化任务：定位解释、跨文件修复、功能开发、测试失败修复、重构、长上下文、取消恢复、权限和对抗输入。至少 10 个任务保留为未参与调优的盲测（用于分析后的下一版必须另留独立盲测）；不同语言、仓库规模与 Windows 路径场景均应覆盖，最终比例在 SP001 固定。
2. 每题有初始仓库快照、指令、可自动断言的预期结果、允许修改范围、外部依赖、时间/token/费用预算及失败分类。以测试、差异正确性和用户目标评分，不以模型自报“完成”评分。
3. 尽量同模型、参数、上下文与工具预算比较；原产品不支持控制时明确分成“同条件可比”和“产品实际效果”两组，不混算因果。每题双方至少独立运行 3 次，记录通过率、样本量与波动，报告总体及分组结果，禁止只选成功案例。
4. 建议最终门槛：安全/权限/会话不串写等确定性保护用例全部通过；关键编码分组不能被总体平均掩盖；可比集完成率相对原产品下降不超过 5 个百分点，实际差距及不确定性完整报告。成本与端到端耗时 p50/p95 同时公开，预算上限 SP001 固定，不能靠无限重试取得通过率。
5. 真实模型不可用、原产品无法合法运行或样本不足时标 UNVERIFIED，并写恢复条件，不能用 mock 结果替代。公开榜单分数也不能替代自己的任务集。
6. SP006 起收集用户真实开发失败，SP021 建议连续两轮完整回归及至少 5 个工作日真实任务试用；新增失败加入回归集并保留原任务集的可比版本，不能通过删除难题提分。

这是可观测行为对齐，不承诺黑盒内部结构相同。完整多代理团队、浏览器/Computer Use、远程/H5、四类 IM 和定时任务现已正式纳入 SP013–SP019；不得用“核心任务通过”替代这些功能的验收。新增能力的具体功能目录、正向/负向场景和组合任务见高级能力计划。

统计限制：30 题×3 次是初始测量方案，不足以自动证明非劣性；分别报告独立任务数量与重复运行的相关性、关键分组和不确定性。结果区间跨越 5 个百分点门槛时结论为“证据不足”，扩充独立样本或运行后再判断；不得只报告点估计。

## 架构与质量要求贯穿每轮

- Core 只依赖自有领域类型和接口，模型、工具、存储、宿主各有明确责任。先稳定最小契约和符合性测试，再扩展；不在本计划强行固定未评审的 API 字段、框架或包目录。
- 工具输入/输出结构化，状态可观测；单会话执行归属明确，取消、超时、重试和副作用恢复有界。禁止将随意 shell 命令检查宣称为操作系统沙箱；执行隔离能力和局限需明确。
- 项目内容、工具输出、Skills/MCP 和 Provider 返回均可能携带不可信指令，不提升授权；凭据日志脱敏、权限默认保守，拒绝之后仍能继续工作。
- 持久化从首次建立 schema 起有版本、原子写/备份、并发策略和旧 fixture；配置/凭据与普通历史的共享和导出策略分开设计，不自动读取旧用户数据。
- 每轮只执行该轮实际配置且适用的检查：单元/契约、真实进程、真实 Provider、UI、安装升级分别记证据。建立 CI 与覆盖率策略后遵守，不降低阈值掩盖失败。
- 各轮都更新需求与 STATUS、文档和诊断说明；获授权的 Git/发布动作另记真实回执。bootstrap 已配置技能、聊天 TUI、版本和安装 smoke 检查；完整 Agent 和高级能力的额外门禁按对应迭代建立，不把首发测试当全部门禁。
