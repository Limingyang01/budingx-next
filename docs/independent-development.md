# 独立实现与复用边界

## 起点

新仓库有助于记录来源和开发过程，但复制旧源码后改名、删除 Git 历史或逐文件 AI 改写，不自动改变来源与许可。工程隔离不能单独作为法律洁净室认证。

旧仓只读保留，不把它设为新产品的代码依赖、运行回退路径或构建输入。实施阶段的行为与效果规格以 [参考实现定位](#参考实现定位) 所述 `budingWorkerSpace` 为严格对照来源；代码实现、公开接口与验收测试仍由本仓独立编写。

## 参考实现定位

用户于 2026-11-16 确认：本仓的设计以及主要核心逻辑必须严格参考本地 `budingWorkerSpace` 参考项目。文档不写死绝对路径：知道存在该参考即可，位置以用户当前机器环境为准（早期 SP 文档中出现过的路径可能已失效，不作为依据）。重点参考范围：

| 范围 | 要求 |
| --- | --- |
| TUI 命令设计 | 命令集合、参数形态与交互行为对齐 |
| Agent 主循环 | 核心机制与状态推进方式对齐 |
| 核心工具 | 工具行为与效果对齐 |

全程绑定：设计文档、实施计划文档和真实开发都必须显式对照该参考，不允许脱离参考开发；允许优化和改进，但逻辑核心不得背离参考机制，使用体验不得下降。对照点在设计与计划文档中逐项列出，偏离参考须说明理由并保持 `CAP-*` 行为锚点可追溯。

复刻方法沿用 SP001 决定 3「读机制、不抄代码」：可读参考项目源码理解机制与算法，实现全部独立编写并改动实现方式，效果一致即可；不逐字复制文件，不搬系统提示词、内部 SDK 类型、全局状态、生成 bundle、配置或历史记录（行为盘点的使用限制见 `SP/SP002/attachments/old-repo-mechanism-inventory.md`）。

许可合规：参考项目仓内无 LICENSE 文件且 package.json 无 license 字段，按其私有未开源事实处理，「遵守 MIT 规则」落实为——本仓自有 MIT 制品不嵌入参考代码、独立可再分发；若日后该参考材料明确授予 MIT 或同等许可，再按其规则保留版权声明与许可文本并登记来源台账与 `THIRD-PARTY-NOTICES.md`。

## 可迁入的条件

每个候选模块记录：来源/revision、作者/许可证据、直接与传递依赖、保留/适配/重写决定、适用范围和验证。新建文件名、近期 Git 日期或“由 AI 生成”不单独证明可直接复用。

- 有明确许可的第三方库和开发技能，按其许可保留声明与必要材料。
- 自有且可独立分发的界面、宿主与工具，审计依赖后逐项迁入。
- 来源不清或耦合旧核心的代码，先隔离，不作为可发布实现。
- 原 Agent 循环、提示词、权限/上下文/全局状态、内部 SDK/type 文件和 bundle 不直接迁入。

## 数据与开发过程

旧模型配置和历史属于保护对象，不是可重建缓存。本次没有导入。将来应明确数据边界，使用只读读取、备份、前向迁移、旧 fixture 和未知字段保留验证；不直接覆盖旧配置目录。

独立实现可以使用公开模型 API/SDK，但必须按各自许可和服务条款处理。接入某模型与再发行该厂商的 Agent 程序源码是不同范围。

## 发布前需要的证据

来源台账、依赖与第三方声明；无旧源码/旧 bundle/旧 CLI 回退；干净环境的实际制品安装与核心行为；权限拒绝/取消/恢复；数据兼容；项目许可证与准确的发布内容清单。

代码相似度、字符串搜索和通过单元测试只能提供部分证据，不能替代来源审计。实际发行授权应按材料及适用法律核对，必要时由专业人士审阅。
