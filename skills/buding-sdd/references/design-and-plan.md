# 设计与计划大纲

按需求规模组织，允许合并章节，不生成空模板。当前产品未实现；拟新增模块、目录、接口与框架应标为提议，不能从旧仓目录推导为现状。简单文档修订不需要完整 SDD。

设计与计划文档须列出对 `budingWorkerSpace` 参考实现的对照点（TUI 命令、核心循环、工具行为；不涉及时说明豁免）；相对参考的优化或偏离须写明理由，核心逻辑不得背离、使用体验不得下降，偏离保持 `CAP-*` 行为锚点可追溯。

## 正式设计

1. 文档头：需求 slug、可选的已确认 SP、版本、draft/approved/superseded、材料来源。区分用户确认、模型提议和开放问题。
2. 背景与目标：具体前后行为、范围、保留行为及实际排除项。
3. 当前状态：现有文件/代码/测试、运行观察和假设分别标注；空仓明确写无产品实现。
4. 方案：责任、输入、规则、状态变化、输出、错误、取消、恢复与兼容性。只写真实可选方案及取舍。
5. 变更集：现有/拟新增文件、真实基线、依赖、消费者、材料来源/许可/处理决定。不能把旧源码换名当成新实现。
6. AC：稳定 ID，Given/When/Then 或同等精度，明确输入、动作、预期结果、边界和测试层；不明需求为 OPEN。
7. 风险与开放项：实现阻塞、启用条件、验证前提；涉及迁移或发布才写相应备份与回滚限制。

| 问题 | 记录内容 |
| --- | --- |
| 谁拥有行为 | 拟定或真实 Core、TUI、客户端、Provider、工具、存储、集成边界 |
| 复用什么 | 本仓已核对的符号/模式，或来源与许可明确的公开组件；新增理由 |
| 跨越什么 | 实际选定的协议/事件/进程契约，不能预设旧路由 |
| 状态放哪里 | 责任方、生命周期、并发、恢复、数据隔离与迁移规则 |
| 谁受影响 | 当前真实消费者及未来接口方向，二者分别说明 |
| 如何失败 | 超时、断线、重复、拒绝权限、取消与进程退出 |
| 如何证明 | AC、最小测试层、真实流程、条件和未验证边界 |

## 实施计划

每个稳定任务 ID 包含：

- 设计段落与 AC、依赖及实际前置产物。
- Create/Modify/Delete/Test 精确路径、责任方及预期接口；拟新增需明示。
- Consumes/Produces：类型或契约、字段含义、所属模块；无新契约时说明复用。
- 目标失败 → 最小实现 → 目标成功 → diff/格式检查 → 状态记录。基础设施报错和零测试不算 RED。
- cwd、真实存在的命令、预期行为及需要的 smoke。框架未定先设计/配置验证入口，不能编造 npm 脚本。
- 完成事实：实际变更、执行数/结果、证据和缺口；不预填 PASS。
- 测试收口映射：该任务覆盖的 AC、单元与功能（端到端）用例、预期 RED 表现与 GREEN 判据；全计划汇总后须保证每条 AC 至少各有一例。

保留 writing-plans 要求的 Goal、Architecture、Spec、Global Constraints、Review Focus 与任务接口。按 [技术栈路由](technology-map.md)确认包、运行时、配置和平台，区分协议 fixture 与真实进程/UI/live/安装验证。

正式设计与计划各产出唯一中文正本（`design.zh.md`、`plan.zh.md`），中文即执行依据，不产出英文版本。设计批准直接覆盖同版计划与后续实施、测试、交付及各阶段完成后的本地提交（提交说明中文）；有效批准绑定范围与版本，恢复不重复批准；实质行为、AC、范围或架构变更才更新相关批准，格式修改不使旧批准失效。AC→任务→用例→测试映射完整，历史放 STATUS，避免互相矛盾的追加稿。
